# 0012. One write path: plan the difference, write only that

**Status:** Accepted. Full description: [../sync.md](../sync.md).

## Context

Rynkbench wrote to the keyboard in four different ways: one key at a time in Live, a loop of single-key writes for the draft's Send (the old Batch), a diff-only import, and a full rewrite of every key and every slot table when a layer moved or was deleted. GLIDE Flows will add bulk changes, and Rynkbench should also work with no keyboard attached.

What the firmware does decides what is efficient. Read in RMK (`colonelpanic8/rmk`, `host/context.rs`, `storage/mod.rs`):

- Each key written is applied at once and appended to flash storage (sequential-storage) **without comparing it to what is stored**. Lighting tables are compared first; keys are not.
- Storage is small (two sectors by default). When it fills, a page is migrated and erased: the slow pause and the wear.
- Keymap writes have no transaction. Lighting tables have begin, put and commit.
- The bulk keymap write saves round trips, not flash: every key in it is still one stored item.

QMK compares before writing (`eeprom_update_*`), ZMK delays and gathers settings writes (60 s by default), and ZMK Studio holds keymap changes in RAM until Save. RMK does none of these for keys, so Rynkbench must.

## Decision

- **The layout you want is the only thing edits change.** The keyboard's state is read, never edited directly.
- **A planner** (`src/sync/plan.ts`, pure) compares a fresh read of the keyboard with the wanted layout and lists only the stored items that differ, in a safe order: create (slots, macros, layer names that become used), then change (keys, encoders, settings, lighting), then remove (slots and layer names no longer used). Keys come as runs of neighbouring cells.
- **A writer** (`src/sync/write.ts`) sends the plan through the session interface: key runs with the bulk command where the firmware has it, Busy retried, stopping at the first failure. It reads the keyboard once at the end and plans again: an empty plan means the keyboard holds exactly what was wanted. After a failure or a dropped link the same comparison gives what is left; resuming needs no bookkeeping.
- **The modes only decide when the writer runs.** Live: keys at once, because RMK applies a key only once it is written (an unchanged key is never sent); lighting and rules 0.6 s after the last change and at once when the page is hidden. Draft: on Send. Not connected: never; the workbench stays open in Draft, the draft is kept per keyboard with what each change was based on, and Reconnect brings it back.
- **A three-way check** guards every Send, including the first after a reconnect: for each item, what you started from, what the keyboard holds now, what you want. Something changed on both sides is shown before it is overwritten.
- **Guard** (ADR 0011) judges the wanted layout before anything is written.
- **Moving or deleting a layer** is a change to the wanted layout like any other: only keys and slots that change are written. The read-back check and the way back on failure stay.
- **`src/sync/` is a new layer** (application service): it may use the model, the domain, the layer rules and the session *interface*, never a backend or the screens. `boundaries.ts` enforces it.
- **The firmware should compare too.** `docs/firmware/` holds a patch for RMK that skips storing a key equal to the stored one, as its lighting code already does. Rynkbench keeps comparing for firmware without it.

## Consequences

- Wear is paid only for what really changed: a layer move writes the keys that move, not the whole keymap.
- One path for one key, a draft, an import, a layer move and a Flow; each is tested once, in the planner.
- A new stored item (a new slot table, a new setting) is one entry in the planner and one in the writer.
- Rejected: holding changes on the keyboard until Save (needs new firmware commands; the client-side draft gives the same experience today); an operation log (comparing two layouts handles imports, Flows, undo and resume more simply); rewriting everything (safe but the most wear).
